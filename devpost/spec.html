Policy Crash Test Approved

One web page, two small server routes, and one calculator that runs in the browser. The AI reads the policy and writes the diaries; every number on screen comes from tested code.

  • Next.js 16.4 · App Router
  • React 19.3
  • TypeScript
  • Tailwind CSS 4.3
  • @anthropic-ai/sdk 0.134
  • zod 4.6
  • Vitest 5.0
  • PARSE_MODEL · claude-haiku-5-5
  • DIARY_MODEL · claude-sonnet-5-5

How it works, in plain language

The town

8 fixed residents in data/residents.ts: income, spending in 9 categories, age, housing type, tags.

Levers

A policy written as numbers: what changes, by how much, for whom. Everything after the input step works from levers.

Presets

4 lever files written and checked by hand. A chip loads one; no AI involved.

The parser

Sends a typed policy to Claude Haiku 5.5 with your prompt; the reply is forced into the lever shape, then checked again.

The engine

Plain TypeScript: levers in, numbers and verdicts out. Same input, same output. Runs in the browser and on the server.

The diary writer

Re-runs the engine, sends Claude Sonnet 5.5 each resident's exact card numbers, streams back one diary per line.

The page

Holds the current run in memory. Nothing is saved; refresh and the town is back to normal.

Why this shape: the AI does only what it's good at, reading messy text and writing in a human voice, while every number comes from tested code. Two routes because there are two prompts; no database because nothing persists.

How data moves

Pick a step to see which pieces it touches. Each step names its files and the PRD heading it implements.

  • AI call (yellow)
  • Tested code
  • Data or file
  • Route or input
  • What you see
    1. Meet the town. The 8 residents load from data/residents.ts; cards show income, spare money and the everyday line.
    2. Pick a policy. A chip loads hand-checked levers; a typed policy goes to the parser.
    3. Reading the policy (typed only). POST /api/parse → Claude Haiku 5.5 → levers, checked with zod.
    4. Running the numbers. The engine updates the summary, chart, cards and panel in place, with no network call.
    5. Writing diaries. POST /api/diaries re-runs the engine and streams one diary per line from Claude Sonnet 5.5.
    6. Done, or partly done. After the stream ends or 20 seconds, missing diaries say "Diary didn't come through"; "Retry diaries" asks for only those.
    7. Next policy. A new run cancels the old diary request; cards change colour in place.

    Testing the AI, not just the engine

    Your learning goal, as three layers, from cheapest and most certain to most realistic:

    1. Shape is guaranteed.Structured output forces the lever shape; zod checks every reply at runtime.
    2. The prompt is tested offline.Its examples must be valid JSON that passes the schema. This is what caught example 4.
    3. Behaviour is measured live.Fixture policies, each run 3 times, because "always" needs more than one run.

    Small technical calls (veto any)

    1. One engine file runs in the browser (instant cards) and on the server (diary input); the server recomputes, never trusts browser numbers.
    2. Money is computed to the cent after each lever, shown in whole dollars.
    3. Each percent change applies to the pre-policy amount, so lever order never matters.
    4. Eligibility bounds are inclusive; "under $3,000" in the preset means "$3,000 or less".
    5. Both models at effort low, no temperature. Parse: max_tokens 4,000, 12 s timeout, 1 retry. Diaries: 16,000.
    6. Refusals are handled before content is read.
    7. Diary lines are checked for shape at runtime; content is checked by the eval.
    8. The diary input carries the exact card strings plus the summary line.
    9. A preset counts only if it came from the chip unedited.
    10. No artificial delays; "Running the numbers" may flash by.
    11. The diary call opts into server-side refusal fallback (fallbacks: "default", beta). It rarely matters here; veto to keep the call plain.
    12. No prompt caching: runs cost cents.
    13. Verdict colours: green #1F8A4C, grey #8A8F98, amber #D98A00, red #C8322B; dark badge text on amber and grey; 300 ms colour change, off for reduced motion.
    14. Household sizes: Lim 2, Faizal 4, Chloe 3 (assumed), Gohs 2, Raju 1, Nurul 2, Marcus 4, Tan 1. Diary context only.
    15. Resident ids: lim, faizal, chloe, goh, raju, nurul, marcus, tan.
    16. Parser cases run 3 times and must pass every time; diaries run 2 times per preset.
    17. The demo is recorded in production mode.
